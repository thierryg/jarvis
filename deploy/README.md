# `deploy/` — deployment artifacts

This directory holds everything that is installed **on the system**: systemd units, nginx,
Anubis, udev and tmpfiles rules, commands in the PATH, the SSH banner and MOTD, monitoring and the
Ansible infrastructure as code. The application code lives in `jarvis/`, the scripts in `scripts/`.

- **Reference platform:** Ubuntu Server 26.04 LTS, x86_64, on a Lenovo ThinkCentre M73 Tiny (see [REQUIREMENTS.md](../REQUIREMENTS.md)).
- **Deployed version:** the one in the central `jarvis/VERSION` file (`jarvis version`, `make version`).

## 1. Deployment methods

| Method | Location | Use |
|---|---|---|
| **Ansible (recommended)** | [`deploy/ansible/`](ansible/README.md) | complete, hardened, verified deployment of a freshly installed server: preflight and postflight checks, firewall, fail2ban, SSH banner, MOTD, local or public TLS |
| Shell installer | `scripts/jarvis-install.sh` | manual installation on the machine itself (no hardening, firewall or MOTD) |
| Docker (local test) | `docker/jarvis-start.sh`, `jarvis-status.sh`, `jarvis-stop.sh`, `jarvis-clean.sh` | try Jarvis on a workstation: self-contained `docker-compose.local.yml`, simulated hardware, HTTPS on `localhost:8443` |
| Docker (host) | `docker/docker-compose.yml` | Compose with the host configuration (`/etc/jarvis`) and devices; development and demonstration |

```bash
cd deploy/ansible && cp inventory/hosts.example.yml inventory/hosts.yml && ./jarvis-deploy.sh deploy   # recommended
sudo ./scripts/jarvis-install.sh --help                                                                 # manual alternative
```

The complete procedure, from the USB key to the first login, is in [INSTALL.md](../INSTALL.md).

## 4. TLS certificates (`jarvis-cert`)

```bash
sudo jarvis-cert issue --mode local --name jarvis.local --ip 192.168.1.20   # LAN, no public domain
sudo jarvis-cert issue --mode letsencrypt --domain jarvis.example.org \
     --email admin@example.org --dns-plugin cloudflare --dns-credentials /root/.cloudflare.ini
jarvis-cert status [--json] [--remote 127.0.0.1:443]    # creation, expiry, remaining time, revocation
sudo jarvis-cert renew [--force]                          # automatic through jarvis-cert-renew.timer
sudo jarvis-cert export-ca --out jarvis-ca.crt            # CA to import on the client devices
```

- **DNS-01 challenge** (Let's Encrypt default): needs **no** port open on the Internet.
- **Exit codes of `status`:** 0 valid, 7 unusable, 8 expiring soon.
- **With Ansible:** choose the mode with `jarvis_tls_mode: local | letsencrypt`
  (see [ansible/README.md §1.3](ansible/README.md#13-choose-the-certificate-mode)).

## 5. Network flow

```
browser ──HTTPS 443──▶ nginx ──▶ Anubis 127.0.0.1:8923 ──▶ API 127.0.0.1:8000 ──unix──▶ jarvis-core
                         └── /api/stream.mjpg, /metrics: straight to the API (no Anubis)
```

- **Port 443:** **never** expose it on the Internet. For remote access, use a VPN (WireGuard, Tailscale).
- **Port 80:** only redirects to HTTPS and serves the optional ACME HTTP-01 challenge.
- **Firewall:** nftables denies all inbound traffic by default. SSH is allowed from the admin networks
  only, and 80/443 from the LAN only.

## 6. Useful commands after the deployment

```bash
systemctl status jarvis.target                 # overall state
journalctl -u jarvis-core -f                   # core log
jarvis                                         # administration shell (help for the list)
jarvis-console                                 # local console (admin password reset: option 3)
jarvis resources --watch 2                     # CPU / RAM / network / GPU / IO
jarvis-cert status                             # certificate
jarvis-motd                                    # SSH dashboard
scripts/jarvis-hwinfo.sh                       # hardware inventory and suitability verdict
systemctl list-timers 'jarvis-*'               # backup and TLS renewal
```

**Default web account:** `admin` / `admin`. A new password is required at the first login.

## 7. Monitoring (`monitoring/`)

This stack is meant for a **separate server** (NAS, VM), not for the mini-PC:

```bash
cd deploy/monitoring && JARVIS_HOST=192.168.1.10 docker compose up -d
```

- **Prometheus token:** put it in `monitoring/prometheus/jarvis_token` (a single line). This file
  is **ignored by git** and must never be versioned.
- **On the Jarvis side:** the agents (node_exporter, Alloy/Promtail, rsyslog) are switched on
  under Settings > Monitoring.

## 8. Conventions

See [AGENTS.md](../AGENTS.md) and [CONTRIBUTING.md](../CONTRIBUTING.md). In short:

- **systemd units:** a header, comments on their own lines (never at the end of a line), maximum hardening.
- **Scripts:** use the shared `scripts/lib/jarvis-common.sh`, functions, colors and documented exit codes; ShellCheck-clean.
- **Secrets:** never versioned (`jarvis.env`, `jarvis_token`, TLS keys, Anubis key, `vault.yml`).
- **Markdown:** every `.md` file is written in technical US English.
